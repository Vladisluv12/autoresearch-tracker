# Общий трекер

Источник состояния — `state.json` в удалённой ветке `origin/coordination`. `BOARD.md` в той же ветке — автоматически обновляемая доска для чтения. Исходники приложения и правила команды находятся в обычных ветках от `main`.

Команды `scripts/coord.py` используют существующий Git remote и его учётные данные. Они читают удалённое состояние и публикуют изменения отдельным коммитом. Push проверяет предыдущий коммит через явный `--force-with-lease`: из двух конкурентных обновлений принимается только одно, проигравшая операция перечитывает состояние. Неудачный `claim` не даёт права работать.

Если для `origin` задан отдельный push URL, трекер читает и пишет именно туда; это должно быть общее репо команды.

Не нужно переключать рабочий каталог на `coordination`, сливать её в `main` или вручную редактировать файлы трекера. Для этой ветки должен быть разрешён прямой push без требований обязательных PR, проверок и подписанных коммитов. Каждый новый коммит продолжает прежнюю историю: разрешать её переписывание или обход защиты от force push не требуется.

## Команды

Во всех примерах `T001`, ID агента, пути и ссылки заменяются фактическими значениями. Запускайте команды из клона репозитория.

```sh
# Один раз на весь репозиторий.
python3 scripts/coord.py init

# Один раз для каждого клона / при изменении роли.
python3 scripts/coord.py identity worker-a --role unassigned
python3 scripts/coord.py whoami

# Задача: scope обязателен, несколько путей и зависимостей разрешены.
python3 scripts/coord.py create "Название" \
  --description "Что требуется" \
  --acceptance "Как проверить результат" \
  --scope src/component --scope tests/component \
  --depends-on T001

python3 scripts/coord.py list
python3 scripts/coord.py show T002
python3 scripts/coord.py claim T002
python3 scripts/coord.py heartbeat T002 --note "Сделано …; дальше …"

python3 scripts/coord.py block T002 --reason "Нужен …"
python3 scripts/coord.py resume T002

python3 scripts/coord.py handoff T002 \
  --summary "Изменения: …; проверки: …; риски: …; ветка: …" \
  --pr https://github.com/dub-otrezkov/claudes-tracker-harness/pull/123
python3 scripts/coord.py done T002 --summary "Принято; PR объединён; проверки: …"

python3 scripts/coord.py release T002 --reason "Передаю работу; ветка: …; осталось: …"
python3 scripts/coord.py takeover T002 --reason "Прежний агент недоступен; проверены ветка и PR …"
```

Если зависимостей нет, не указывайте `--depends-on`. `--pr` можно опустить, если результат не является PR; укажите, где он доступен, в summary.

Идентичность хранится в локальной Git-конфигурации. `COORD_AGENT` и `COORD_ROLE` имеют приоритет над локальными значениями. Не передавайте один `agent-id` двум одновременно работающим процессам: трекер не отличит их друг от друга.

## Области работы

Каждая задача резервирует один или несколько путей от корня репозитория. Путь может указывать на файл либо каталог, включая будущий. `src/api` пересекается с `src/api/routes.py`; одинаковые пути также конфликтуют. Используйте обычные относительные пути без `..`, абсолютных путей и glob-шаблонов. Единственный специальный вариант — `*`, он охватывает весь репозиторий.

Резервирование действует в состояниях `doing`, `blocked` и `review`. Оно освобождается после `done` или `release`. Задача с невыполненными зависимостями не может быть взята. Лучше заранее разделить общие файлы, интерфейсы и интеграцию на отдельные задачи, чтобы агенты могли работать параллельно.

## Владение и состояния

| Действие | Результат |
| --- | --- |
| `create` | Новая задача без владельца |
| `claim` | Владелец получает задачу; статус `doing` |
| `heartbeat` | Подтверждается владение и обновляется время активности |
| `block` | Статус `blocked`, владелец и область сохраняются |
| `resume` | Собственная заблокированная задача возвращается в `doing` |
| `handoff` | Статус `review`, владелец и область сохраняются |
| `done` | Работа принята; область освобождается |
| `release` | Задача снова доступна для назначения, область освобождается |
| `takeover` | Просроченная задача передаётся другому агенту с записью причины |

Изменять взятую задачу может её владелец. `takeover` — предусмотренное исключение после истечения срока активности. Назначенная роль сама по себе не даёт права менять чужую задачу.

Посылайте heartbeat примерно каждые 10 минут, в том числе при ожидании проверки, если задача остаётся вашей. После паузы, перед возобновлением правок, коммитом или push сначала дождитесь успешного heartbeat. При ошибке связи или потере владения остановите изменения и получите актуальное состояние через `show`.

## Если агент пропал

Через **30 минут** без обновления активности задача считается просроченной, но автоматически не освобождается. Это сохраняет контекст незавершённой работы и предотвращает молчаливое назначение ещё одного исполнителя.

Время записывается в UTC, а возраст heartbeat и доступность `takeover` рассчитываются по локальным часам участников. Включите автоматическую синхронизацию времени на каждой машине: неверные часы могут привести к слишком ранней или поздней передаче задачи. Часовой пояс интерфейса при этом может быть любым.

1. Прочитайте `show`, последнее сообщение, ветку и PR. По доступному каналу предупредите прежнего участника о передаче работы.
2. После 30 минут без активности выполните `takeover` с содержательной причиной. Только успех этой команды подтверждает нового владельца.
3. Продолжайте в своей ветке. Сначала проверьте незавершённые изменения предшественника, чтобы не потерять полезную работу.
4. Вернувшийся прежний агент обязан проверить владение через heartbeat. При отказе он прекращает работу по задаче и передаёт оставшийся контекст новому владельцу.

Трекер защищает согласованность назначений между соблюдающими правила агентами. Он не блокирует файловую систему другой машины и не останавливает забытый процесс. Любой участник с правом записи в репозиторий технически может обойти CLI: это протокол координации, а не разграничение прав доступа. Поэтому проверка владения и согласование веток обязательны при восстановлении.

## Передача результата и интеграция

В summary и PR укажите:

- что изменилось и какие критерии приёмки выполнены;
- проверки и результат, включая невыполненные проверки;
- риски, ограничения и оставшиеся вопросы;
- ветку, коммиты и ссылку на PR или другой результат.

`handoff` означает готовность к проверке, а не завершение задачи. Пока идёт review, область остаётся занятой. Ответственный за интеграцию из `TEAM.md` проверяет PR и объединяет его; затем владелец выполняет `done`. Если нужны исправления, владелец продолжает с проверкой heartbeat, в своей ветке и в прежних границах задачи, после чего обновляет handoff.

Если интегратор ещё не назначен, сохраните результат и PR в `review`; распределение ролей должно определить, кто принимает и объединяет работу. Для задач без кода завершение определяется критериями приёмки.
